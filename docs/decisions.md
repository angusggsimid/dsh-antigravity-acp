# 决定

从这次把 Gemini 接到 DSH 的过程里留下来的结论。日期是 2026-11-07。

## 聊天走 ACP，不走旧的 HTTP 桥

旧桥把本机请求转成远端的 `agy` 调用，并且曾经要清洗工具 schema。ACP 让官方进程自己说话，DSH 只做 JSON-RPC。工具调用回到本机执行，不让 `agy` 在远端改文件。

已经从 profile 和项目里去掉的旧插件：一次性的 `gemini` CLI 工具、`/boost`、以及每次启动就打一条测试请求的 tool-fix-check。它们和 ACP 会话无关。

## 额度留在 HTTP 桥上

设置页和输入框左边的「5 小时 / 每周」不是某一轮的 token。ACP 的 `initialize` 和 `session/new` 里没有这些窗口；`session/prompt` 的 `usage` 只统计这一轮。

官方对外给出这组数字的方式是 `agy -p /usage`。现有 HTTP 桥已经在这么做。曾经考虑过改成每次刷新再 SSH 一次，那样可以拆掉常驻的 bridge 进程。每次查询本身仍要拉起 `agy`，两边一样，所以额度继续走原来的桥。地址不写在仓库里。

输入框上的数字和设置页是同一份缓存：先显示上次的结果，超过 1 分钟才刷新，大约每 5 分钟再查一次。

## 一个插件

订阅页面、徽章和 `gemini_quota` 工具并进 `antigravity-acp`。插件列表里不再单独出现「Antigravity 订阅」。设置里的那一节标题仍然叫「Antigravity 订阅」。

## 会话怎么配对、怎么回收

- DSH 会话和 ACP 会话是本地映射，不是同一个 id。
- 键是 `会话:用途`。主对话、标题、子任务分开，避免互相挡住。
- 软上限 3：新会话进来时，关掉最久没用、而且现在不忙的会话。
- 硬上限保持很小：没有空闲会话可关时直接报错，避免把远端机器打满。
- 空闲 2 分钟后关闭。清扫周期 60 秒，所以实际大约在 2 到 3 分钟内发生。
- 关掉后再开口，`session/resume` 必须回到原来的 ACP 会话，而不是新建。做不到时才新建并重放。
- 刚创建、还没开始输出的会话不算空闲，避免被下一次请求立刻挤掉。

这些上限来自对 `agy` 的测量：每个会话的 worker 都不小，而且 ACP 这条路不会自己收 worker，只有 `session/close` 会。机器更大时再在本机配置里调高。

## 系统提示有两条路

远端 agent 文件的正文就是系统提示，这是官方有的行为。静态规则放在那里。DSH 随回合传来的系统提示仍用 `_meta.antigravity.systemPrompt.append`。这个键没有写在公开文档里；关掉它之后，静态规则还在。

## 没有做成的事

- 不把 Claude / GPT-OSS 放进这个插件。只要 Gemini 3.8 Flash。
- 不把额度查询塞进某条 ACP 对话。那会污染会话，也不适合每 5 分钟查一次。
- 不把每会话一个 tenant 的 MCP 改成全局一份配置。全局配置才能写 `timeoutSeconds: -1`，但会丢掉「这条工具调用属于哪个会话」。180 秒上限仍用 85 秒中继和 `dsh_await_result` 绕开。
